## 原因与证据

此前正式版应用日志：Contents API 在 576ms 返回 403，Gcore 在 1601ms 返回 404，TestingCF 在 2499ms 返回 404，Fastly 在 8410ms 返回 404；其余来源在约 10000ms 超时，最终显示 Network。另一次官方 Raw 在 1323ms 返回 404，但原实现只有 Contents API 指针 404 能确认未发布，因此仍等待其他来源。403 是更新服务拒绝请求，不能证明用户网络断开。

开启测试版后代码并发查 beta/stable，原聚合使用 awaitAll，必须等两个渠道结束。先将请求预算从 1.5 秒扩大到 10 秒却没有改变渠道返回条件，会放大等待慢渠道的时间。这是代码中确认的问题；没有 beta 应用现场计时日志，不能将模拟场景表述为用户手机这次检查的完整过程。

此前接受的 beta 策略编号 2 与历史签名清单一致，当前线上编号 1 来自发布记录丢失后重新计算。发布脚本读取当前树中 latest 与不可变清单编号取最大值加一，旧记录丢失后从 1 开始。客户端保留防回退是正确行为。本次提供明确过期提示，未放宽校验或修改线上清单；发布侧恢复连续编号仍需单独处理。

## 修改后的行为

- 一个渠道得到有效清单后最多再收集另一个渠道 300ms，取消未完成请求；全部完成则立即返回。
- 来源仍保留 300ms 收敛窗口，按权威优先、签名有效与冲突拒绝选择。来源收敛可跨过首个来源等待期限，渠道期限留出余量。
- Contents API 指针 404 确认未发布；官方 Raw 指针 404 且窗口内没有 Contents API 有效清单时，也确认未发布，不等镜像超时。有效 Contents API 清单优先于 Raw 404。普通 CDN 404、不可变清单 404 不能独立证明未发布。
- 一渠道有新版本而另一渠道未完成，返回有效新版本；一渠道没有新版本或另一渠道有更高的已知更新，返回部分检查并提示哪个渠道不可用，保留已知更新，不自动打开旧详情。
- 只更新已确认渠道的缓存。未完成渠道原有可用状态不变；部分完成即使找到新版本也按 1 小时冷却重试，手动检查仍绕过冷却。
- 无可信清单且收到 HTTP 403/503 等服务错误时提示更新服务暂时不可用；I/O 错误或超时才映射网络错误。
- 过期/策略回退、同编号冲突、无效签名分别反馈，保留已接受策略与强制要求。
- 日志记录成功来源的指针/清单耗时、整个检查耗时与已完成渠道，不记录正文、账户或设备标识。

单请求 10 秒、首个来源等待 21 秒、整体 22 秒都是上限，不是固定等待。
