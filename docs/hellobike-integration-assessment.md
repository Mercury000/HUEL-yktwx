**实施更新（2026-11-13）：** 已在独立目录 `D:/mercu/Desktop/yktwx-hellobike`、`feature/hellobike` 分支完成普通单车网络骑行及普通付款适配。共用入口、账户、设备展示与支付界面的当前行为见[实施说明](life-devices-hellobike.md)。下面保留 2026-11-12 的评估背景与原型缺口，不代表当前实现仍缺少这些能力；真实车辆和扣款尚未核验。

评估日期：2026-11-12。来源为 `D:/mercu/Desktop/hellobike` 的当前有效源码、Gradle、清单、测试源码和说明文档；目标为财小通当前工作区，包含尚未提交的统一 OkHttp 网络层。后续使用 REA 对照 `D:/mercu/Downloads/哈啰_7.0.75.apk` 的支付、结算入口及车号规则，范围见[支付分析](hellobike-payment-analysis.md)。最新[接入补证](hellobike-integration-evidence.md)增加了官方登录、银联SDK和公开H5单车付款参数来源，并按用户要求将支付范围收窄为余额、支付宝和普通银联，排除微信SDK渠道。未读取账号文件、重放凭据或请求真实业务接口，未执行构建和测试；仅额外读取官方公开静态页面和脚本。

**结论：可以接入现有生活服务体系，改动规模中等。按用户要求，共用 798／胖乖的扫码、设备页、登录、账户管理、进度展示和前后台恢复机制；接口与订单状态按哈啰协议适配。现有证据已覆盖单车待付详情到通用支付组件的连接，余额、支付宝、银联具备具体适配依据；尚不能证明整合后能够在真实车辆上完成骑行或结清。**

## 1. 接入形式

使用付款页现有「扫一扫」识别哈啰单车码，在现有 `Screen.LifeDevice` 内展示车辆、计费规则、开锁和还车状态。识别后等待对应平台账户恢复，未登录时使用同一设备页的登录提示与登录抽屉；登录成功继续处理原扫码结果，不自动开锁。骑行中和结果待确认时，通过付款页现有胶囊岛返回该订单。

账户放入现有「设置 → 生活服务账户」，复用核验、登录、换账号和退出入口。页面切换、相机释放、前后台暂停／恢复、加载提示、错误提示、操作禁用、深浅色、动画和预览模式遵循现有机制。

用户不需要进入另一套单车控制台。来源中的 `MainActivity`、`LoginActivity`、扫码 Activity、独立底栏、玻璃主题、诊断导出和「连接真实账号」开关不整体迁入。登录与开关锁仍需用户主动操作，使用项目现有须知与在线业务入口约束。

源码定位：[YktApp.kt](../app/src/main/java/com/mercury/yktwx/ui/YktApp.kt)、[LifeDevicePages.kt](../app/src/main/java/com/mercury/yktwx/ui/pages/LifeDevicePages.kt)、[Hui798Pages.kt](../app/src/main/java/com/mercury/yktwx/ui/pages/Hui798Pages.kt)。

## 2. 扫码为什么出现数字位数判断

现有二维码主要按域名、路径和参数识别；代码另保留裸编号兼容，而且相机结果与手动输入调用同一个解析器。因此数字位数判断既能接受手输编号，也会作用于相机返回的纯数字内容。

| 服务 | 当前链接识别依据 | 当前裸编号兼容 |
| --- | --- | --- |
| 胖乖接水／淋浴 | `https://h5.qiekj.com/skip`，`SN` 参数 | 15 位纯数字 SN |
| 胖乖洗衣 | 同域名与路径，`NQT` 参数 | UUID 形式 NQT；文档注明真实洗衣原始二维码格式仍待证实 |
| 慧生活798 | `i.hnkzy.com/q/1/...`，或 `cloud.hnkzy.com/h5/` 的明确设备参数 | 不接受裸数字，要求链接包含平台身份 |
| 轻骑原型 | `http(s)://c3x.me`，`n`／`u` 参数 | 4～16 位纯数字车号 |

依据：[DeviceSerial](../app/src/main/java/com/mercury/yktwx/data/life/LifeDeviceModels.kt) 第 74 行起、[LifeDeviceCode](../app/src/main/java/com/mercury/yktwx/data/life/LaundryModels.kt) 第 10 行起、[UnifiedDeviceCode](../app/src/main/java/com/mercury/yktwx/data/life/Hui798Models.kt) 第 10 行起，以及来源 `ScanParser.java`。

前次提到的冲突仅指裸编号兼容重叠：15 位数字同时落在胖乖 SN 和轻骑车号范围内。**这不会造成不同域名二维码之间的冲突，也不是增加按数字位数分流的理由。**

REA 补证：官方 7.0.75 的普通单车手动输入创建 `TextChangeWatcher(super(10))`，在长度等于10时触发完成；`c3x.me` 的扫码解析方法则按域名和注册参数取编号，没有位数检查。因此原型的4～16位宽松范围不应直接作为官方规则。明确哈啰上下文的普通单车手输编号可按10位处理；完整域名链接不能仅凭这一手输规则推定必须为10位纯数字。依据与限制见[车号分析](hellobike-payment-analysis.md#5-官方车号是不是-10-位)。

接入时采用以下职责：

- **域名确定平台，路径和参数确定业务，编号格式仅校验字段。** 在统一扫码路由中增加 `c3x.me` 的普通单车分支；不将轻骑「任意 4～16 位裸数字」分支加入跨平台自动识别。
- 共用手动输入继续允许完整二维码链接。哈啰裸车号仅在已有明确平台上下文时解析；统一入口里无法确定平台的裸数字不猜测为哈啰，也不增加专用车号页面或预先选平台流程。
- 既有胖乖裸 SN／NQT 兼容属于现有行为。本次评估不主张直接删除；若统一入口后续改成只收完整链接，应同步调整提示、相关调用和兼容测试。
- `c3x.me` 仅在本机解析，不访问二维码链接或跟随跳转。允许明确的 `n`／`u` 单车参数，拒绝其他车型参数、重复参数、不同车号并存和伪造主机。来源当前允许相同值的 `n`、`u` 并存及跳过空值，README 关于一律拒绝并存的描述已过时。

因此，接入不需要更换相机或二维码识别库，主要是扩展解析后的路由。现有 [DeviceScanner.kt](../app/src/main/java/com/mercury/yktwx/ui/components/DeviceScanner.kt) 第 71 行起已将识别结果作为字符串交给业务。

## 3. 能复用什么

| 部分 | 接入选择 | 理由 |
| --- | --- | --- |
| 相机、二维码解码、手电筒、手动输入、退出转场 | 复用财小通现有实现 | 与平台协议无关，不增加 JourneyApps 扫码 Activity |
| 设备页外壳、登录抽屉、加载和错误提示、操作底栏 | 复用现有组件 | 单车信息和操作作为共用设备页的业务内容 |
| 设置中的生活服务账户、登录提醒、恢复等待 | 扩展现有平台分派 | 统一入口和行为，保持凭据独立 |
| 付款页进度岛 | 复用现有展示与交互 | 增加骑行图标、状态及平台路由，不复制一套进度 UI |
| HTTP 传输 | 复用 `AppHttp.service` 与 `readResponse` | 已有连接池、协程取消、禁重定向和禁止自动重放业务操作的规则 |
| 加密保存 | 复用 `SecureVault` 基础设施，使用哈啰独立命名空间 | 保存账号与订单，保持原型的密钥失效恢复能力及待确认操作记录 |
| 账号核验与迟到响应隔离 | 复用 `LifeAccountVerifier`、任务取消、代次和账户归属模式 | 导入不等于服务端已验证；不同账户响应不能写回当前订单 |
| 哈啰登录／骑行接口、错误映射、订单状态 | 迁移并适配来源实现 | 这是新增平台必须提供的协议能力 |
| 定位与行政区反查 | 增加小范围平台能力 | 当前生活服务不要求定位；哈啰预校验、开锁和还车需要新鲜位置 |

复用边界与胖乖洗衣现有做法一致：共用账号机制、传输和布局，业务使用各自协议状态。不能把哈啰订单号和状态值直接当成 `WaterPhase` 或 `LaundryPhase`；可以将它们映射到同一套展示状态与操作组件。

## 4. 当前项目需要调整的公共位置

现有结构可以扩展，但尚不是增加一个枚举值就完成的平台体系：

- `LifeProvider` 目前只有胖乖和798，`LifeFeature` 只有接水和洗衣，需要增加哈啰／骑行的明确身份。
- `YktApp.kt` 第 373、525、531、548、798、817 行附近存在两平台分派。新增平台要使用明确分支，避免「不是798就调用胖乖」。设备展示继续使用现有 `Screen.LifeDevice`。
- `ManagedLifeAccount` 在 `LifeAccountsSettings.kt` 第 23 行起将非798平台的名称、服务和标记全部当成胖乖；应改为各平台元信息。
- `ThemeSettings.kt` 的登录提醒保存、`LifeDeviceStatusIslands.kt` 的图标与功能分派也依赖两类服务，需要同步扩展。
- `PaymentPage.kt` 已有 `additionalLifeEntries` 扩展位；可沿用进度入口，但现有 `LifeDeviceStatusEntry` 主要依赖 feature，需为跨平台点击和移除提供明确平台身份。
- `UsageNotice.kt` 当前未披露哈啰和定位；增加对应接收方、数据用途与位置权限说明，沿用现有正文变更和同意机制。

建议先把这些公共位置改成明确的平台分派，再接入哈啰适配。无需先完成 [modernization-assessment.md](modernization-assessment.md) 的 Hilt、DataStore 或 JSON 全面迁移；若这些工作随后实施，哈啰跟随项目统一迁移。

## 5. 来源实现与可靠性问题

### 5.1 已具备的业务基础

来源实现了短信登录接口、账号／HAR／Token 导入、预校验、价格规则、创建订单、订单查询、还车位置校验、关锁提交和结束信息读取。`RideFlow.kt` 第 61、91 行在发送开关锁前切换状态并调用持久化，发送后只轮询，不自动再次创建或关锁。最新原DEX注解补证确认预校验、创建与还车action，但没有取得原型这些接口的当前成功响应，不能仅凭action一致推断两种客户端环境可直接混用。

登录成功后保存 token、ticket、userGuid 及行政区信息；当前 UI 没有滑块交互，也没有自动刷新会话。支付目前只读取开锁前 `priceRule` 和结束后的 `payAmount`，没有付款提交或结清查单。REA 确认官方原生支付链路调用 `com.alphapay.paymentOrder.pay`，再以 `com.alphapay.facade.orderSingleQuery` 返回 `payStatus == 1` 确认支付成功；公开单车待支付H5现已确认从`user.artemis.pay.page.order.detail`及`unpaidPayList`取得付款标识、金额和业务类型。因此接入要分别记录骑行结束与费用结清，继续复用设备页和进度入口展示待支付／待确认状态。官方免密、骑行卡和抵扣条件尚未完整核实，不能认定还车后自动结清。详见[支付与结算分析](hellobike-payment-analysis.md)和[参数与状态补证](hellobike-integration-evidence.md#3-已补齐的单车付款链路)。

预校验和还车位置确认不增加本机时限；骑行发现按官方 `user.ride.bikeCheck` 的空结果语义处理，不单独解释业务码301。返回订单标识匹配、未知结果不显示成功和关锁后只读核对用于保护结果完整性。当前实现与逐项依据见[云端判断与原文提示核验](life-cloud-authority-audit.md)。

### 5.2 接入前应修正的具体缺口

| 缺口 | 当前证据与影响 | 接入处理 |
| --- | --- | --- |
| 登录 UI 未实现滑块交互 | `LoginApi.java` 有滑块读取与提交方法；`LoginActivity.kt` 第 254 行遇到滑块直接提示转官方 App，`SliderChallengeView` 未接入当前页面 | 不能宣称完整滑块登录已可用。使用共用登录抽屉接入真实交互，或明确按现有官方处理提示终止该分支 |
| 短信登录绕过订单归属处理 | `MainActivity.kt` 第 143 行的导入／Token 替换会核对 owner；`LoginActivity.kt` 第 265 行直接 `SessionStore.save` | 所有登录方式走同一账户接入路径。换账号取消并等待旧任务，旧订单按原用户隔离，不沿用到新账户 |
| 开关锁记录保存未确认成功 | `MainActivity.kt` 第 133 行使用普通 SharedPreferences 保存订单、车号、owner、阶段；第 140 行忽略 `commit()` 返回值 | 改为共用加密记录及可失败的原子保存；待提交记录未可靠落盘时停止发送命令 |
| 登录任务生命周期不完整 | `LoginActivity.kt` 第 56 行创建手动 CoroutineScope，未在销毁时取消；`Gateway.java` 为阻塞连接 | 改为项目现有 ViewModel／协程与可取消 HTTP；账户切换、离页后防止旧请求继续写回或结束新页面 |
| 还车额外确认条件不完整 | README 声称只接受含 `skipConfirm=true` 的路径；`RideFlow.kt` 第 85 行只校验 status、causeType、penaltyFree | 核对并严格处理额外确认、费用和异常停车字段；未实现的分支转官方处理，不按普通成功路径提交 |
| 密钥失效会影响待确认订单恢复 | 来源 `SessionStore` 支持换密钥重新导入；目标 `SecureVault.read` 在解密失败时移除对应记录并返回空 | 复用加密基础时保留失败与恢复语义。不能把无法读取记录当成确认无订单；重新登录后先查询服务端 |

账号退出入口、取消、等待和界面行为与798／胖乖保持一致；订单归属、待提交记录和服务端核对由平台适配负责。退出或换账号不结束真实骑行，恢复过程中不补发开关锁。哈啰具备服务端骑行查询，重新登录后可查询正在骑行的订单；已知但结果未知的提交还需要按原订单标识核对。

### 5.3 未验证的服务端条件

来源没有 BLE 控制、离线开锁、WebSocket、官方风控签名和设备指纹实现，也没有支付、骑行卡、实名认证、复杂验证码及异常停车完整流程。适用范围仅是服务端允许、车辆支持的普通单车网络操作。

`LoginActivity.kt` 第 244 行取当前 APK 证书并生成 `apkSignHash`。整合后证书、包名、客户端环境发生变化，后端是否接受必须验证，不能从源码推导成功。实施阶段已按用户要求使用离线复算的官方公开证书哈希作为固定请求字段；本项目 APK 仍使用自己的签名，见[客户端身份](hellobike-client-identity.json)。原型 `RegionApi.java` 的反查签名为固定占位字段；实施已替换为官方公开 H5 算法，保留反查失败后的手动地区回落。两项均未在线核验。

涉及定位时新增前台精确／粗略位置权限，并按设备页和操作生命周期获取位置。保持坐标格式与转换一致，由云端判断位置，不增加本机位置时限、误差阈值或模拟位置标记的业务拒绝。仅移植网络流程不需要新增 BLE 控制权限；增加官方 App 的包可见性以支持现有异常处理动作即可。

## 6. 工具链与证据范围

来源与目标同为 Kotlin／Compose／Miuix，`compileSdk` 均为37。来源实际 `minSdk=33`，目标为34，因此接入不需要提高目标最低系统版本。来源用 Kotlin 2.4.10、Miuix 0.9.3、Java 17；目标用 Kotlin 2.4.21、Miuix 0.9.4、JDK 22。迁入代码使用目标依赖、构建和签名配置，不复制来源 Gradle 或调试签名，也不引入另一套 Compose 版本。

来源有效主代码约29个 Kotlin／Java文件、3,788行，含较多独立 UI；实际应迁移的协议／状态代码小于这个规模。测试源码静态计数为52个 `@Test` 方法；README 仍写41项和旧依赖版本，不能把历史测试结果当作当前52项已全部通过。README 还称支持 Android 9，而实际 Gradle 是 Android 13起；当前 Kotlin 登录 UI 的滑块能力也与说明不一致。

接入结构结论来自源码阅读与对照；支付与车号结论另有官方 APK 静态证据。首次方法分析仅覆盖两个原始DEX；最新补证分别增加登录、银联和网关三个原始DEX切片，以及官方公开待支付H5静态脚本，仍不覆盖全APK和在线业务可用性。没有运行测试。源码未包含独立 LICENSE／NOTICE；如合并后公开分发，应明确该代码的授权来源与必要归属。账号、HAR 和签名材料不作为代码或资源迁入。

## 7. 实施和验收建议

1. 扩展公共平台身份、域名路由、账户元信息和进度点击分派；继续使用现有设备页面和相机。
2. 适配哈啰登录、订单和定位接口到当前网络层，迁移状态与错误映射；统一账户隔离、持久化和任务取消。
3. 在共用设备页、登录抽屉、账户设置及进度岛中提供骑行内容；沿用现有交互、样式与预览限制。
4. 只验证本次直接相关路径：三平台扫码分流、账号恢复与换账号、保存失败不发送命令、开关锁单次提交、取消／超时／重启后查单、订单不匹配、还车额外确认、设备页和进度入口。复用原型有意义的状态与响应测试，历史 HAR 导入测试改用脱敏 fixture。
5. 发布可用性需设备和车辆证据：本人账号在整合包内登录或核验、真实域名二维码、定位／行政区、预校验与价格、单次开锁及服务端确认、还车及结束确认。遇到蓝牙、额外认证或停车费用走官方处理。离线测试不替代该验收。

**可按现有生活服务模式接入正常网络开还车，按服务端可用渠道适配余额、支付宝、普通银联结清，异常或未支持渠道在官方处理。最新协议补证不等于真实业务已验证；“至少可用”的验收门槛见[补证与实施边界](hellobike-integration-evidence.md#7-至少可用的验证门槛)。**
