# 代人充值接口调查

核验日期：2026-10-22（Asia/Shanghai）。通过 MCP 读取已登录官网的代人充值组件源码，并查看用户手动查询产生的网络请求。**本次未提交新的收款人查询，未创建订单、支付、挂失或解挂。** 原始请求、Token、Cookie、证件号、学号、验证码及个人响应不写入仓库。

## 验证等级

- **用户手动查询的实际响应**：验证码错误；验证码通过后查询目标账户不存在。
- **当前官网源码确认**：查询参数、验证码交互、成功判断、卡片/电子账户映射、代充值下单字段、签名和支付链路复用。
- **未验证**：代充值成功查询、跨用户收款目标下单、收款对象在收银台/订单中的回显、代充值支付及到账；无 Cookie 的收款目标查询与下单也未验证。

不要将已有的本人充值成功 HAR 视为代充值链路已验证。现有本人充值协议另见 [充值调查](recharge.md)。

## 1. 官网入口与查询类型

当前入口：

```text
/campus-card/cardRecharge?rechargeType=sno-id&appId=56&loginFrom=h5&synAccessSource=h5
```

`rechargeType=sno-id` 让同一充值组件显示两种查询方式：

| `idtype` | 页面含义 |
| --- | --- |
| `sno` | 学工号 |
| `id` | 证件号 |

源码还包含 `acc`、`cardid`、`phone` 类型，但当前入口未启用，不能直接作为已验证功能开放。入口 `appId=56` 是服务入口标识，不是下单签名用的 `appid` / `APP_ID`。

## 2. 验证码

```http
GET /berserker-auth/oauth/captcha?synAccessSource=h5
synjones-auth: bearer <access_token>
synAccessSource: h5
```

当前图形验证码组件从响应**顶层**读取 `key`、`image`；用户输入验证码后再提交收款人查询，使用 `captcha_header_key`、`captcha_header_code` 两个查询参数。它们不是本次查询的 HTTP 请求头。

当前官网查询按钮先打开验证码弹窗；错误时刷新验证码并清空输入。不要自动识别、绕过或重复重放验证码，不把验证码键值或图像写入日志。源码也有滑块验证码分支，但本次仅观察到图形验证码，不接入未验证分支。

## 3. 查询收款卡片

```http
GET /berserker-app/ykt/tsm/idtypeQueryCard?idtype=<sno|id>&id=<user input>&scene=recharge&captcha_header_key=<key>&captcha_header_code=<user input>&synAccessSource=h5
synjones-auth: bearer <access_token>
synAccessSource: h5
```

查询必须是用户主动输入的目标，不枚举学号或证件号；参数 URL 编码，服务端日志和客户端日志均应避免记录完整查询 URL。

当前源码成功条件为外层 `code=200` **且** `data.retcode="0"`，卡列表取 `data.card[]`。还需要确认返回了可选卡片/账户，不能只凭外层成功继续下单。此成功分支仅由源码确认，本次没有成功查询响应。

实际观察到两类错误（均为 HTTP 200）：

```json
{"code":8002,"success":false,"data":null,"msg":"验证码有误"}
```

```json
{
  "code":200,
  "success":true,
  "data":{
    "retcode":"60003",
    "errmsg":"账户信息不存在",
    "account":"<redacted>",
    "sno":null,
    "card":null
  },
  "msg":"操作成功"
}
```

第二种响应的外层 `success=true` / `msg="操作成功"` **不是查询目标成功**。内层 `60003` 才是业务失败；停止流程、清空已选收款人和账户，优先显示 `data.errmsg`。验证码失败使用外层 `msg`，刷新验证码让用户重新输入。目标变更或查询失败后，不能保留旧目标继续充值。

## 4. 从目标响应选择充值账户（源码确认）

沿用官网 `eachCardList` 映射，不能把输入的学工号/证件号直接作为下单 `yktcard`：

- 卡账户模式：`yktcard = card.account`。
- 电子账户模式：`yktcard = card.accinfo[].type`；同时保留其父卡片 `account`，用于绑定本次查询目标与确认信息。
- 当前 `ecardConfig.type="1"`，官网只展示电子账户候选。
- `showLost`、`freezeRecharge` 控制挂失/冻结卡片是否可充值；本次观察值分别为 `"1"`、`"0"`。按源码，当前官网允许挂失卡进入候选，冻结卡禁用；这不是已实测的服务端承诺，也不代表客户端应绕过自身更保守的限制。
- 多候选时官网提供选择器。客户端应明确展示后端返回的完整收款人、卡片/账户和金额，不能将第一项静默当作用户确认。
- 卡片余额字段以分表示，充值金额以元表示。

成功返回中的姓名、学号、卡片账户、电子账户类型和状态字段仅由组件解析逻辑确认；未观察到本次代充值成功响应，不承诺其字段始终存在。

## 5. 代充值下单（源码确认，未提交）

复用本人充值配置 `frontConfig.recharge`（本次 `401`），以及签名表单：

```http
POST /charge/order/thirdOrder
Content-Type: application/x-www-form-urlencoded
```

| 字段 | 代充值取值 |
| --- | --- |
| `feeitemid` | 配置中的充值项目，不固定为永久常量 |
| `appid` | 当前官网前端接入标识 `56321`，不是入口 `appId=56` |
| `tranamt` | 用户确认金额，单位元 |
| `source` | `app` |
| `synjones-auth` | **付款人当前登录 Token**，只提交固定学校 HTTPS 源站 |
| `yktcard` | 本次收款目标查询后选中的卡账户/电子账户 ID |
| `synAccessSource` | 当前载体，本次 `h5` |
| `abstracts` | JSON 字符串 `{"type":"recharge","othersRecharge":true}` |
| `APP_ID`、`TIMESTAMP`、`SIGN_TYPE`、`NONCE`、`SIGN` | 与本人充值相同的官网签名过程 |

官网用 `Boolean(queryType.key)` 生成 `othersRecharge`，而不是单独的代充值支付接口。查询中的 `idtype`、`id`、验证码字段**没有被显式加入这份下单表单**；不能自行增加未确认字段，也不能假定只改布尔值就能正确路由收款人。

**关键未验证边界**：尤其在电子账户模式，需要真实成功查询和用户确认下单来验证 `yktcard` 与目标绑定的服务端语义，确认收银台/订单回显的是预期收款人。不要凭电子账户类型字符串推断跨用户目标一定正确，不复用旧查询结果，不从本人账户接口回退选取同名账户。

普通网页走上述表单下单；AI 聊天组件另有 `/charge/cashier/toPayment` 分支，本次没有调用。签名细节见 [充值调查第 3 节](recharge.md#3-创建学校收银台订单源码及微信内-har-确认)。

## 6. 支付与结果核验

源码复用学校收银台流程：

1. `GET /charge/pay/getpayinfo` 读取本次订单及可用支付方式。
2. `POST /blade-pay/pay` 提交用户确认的支付。
3. `GET /charge/order/personal_data` 核验匹配订单结果。

这些路径在本人充值中已有验证，但**本次代充值没有订单，未调用这些步骤**。校验订单号、金额、收款目标和项目；目标字段缺失或无法核验时不要声称代充值到账。不要用付款人余额增加来判断收款人到账，不因回跳、HTTP 200 或支付调用返回就显示成功。

## 7. 当前 Android 实现（2026-10-22）

付款页“生活缴费”下方的“校园卡服务”提供“挂失 / 解挂”“代人充值”两个图标，保持同样三列网格供后续扩展。

- `CardServiceApi` / `CardServiceViewModel` 实现用户图形验证码输入、收款人查询、选择目标和充值配置加载；编辑收款人、查询失败、关闭或切换登录账户会清除旧目标。
- 单独读取充值项目和限额，**不调用付款人 `queryCard` 回退选择目标**；挂失、冻结或明确异常的目标不进入当前原生候选。
- `RechargeConfiguration` / `PendingRecharge` 携带内存中的所选收款目标；下单按该目标的 `targetId` 设置 `yktcard`，`othersRecharge=true` 参与现有签名过程。
- 查询完成后用户显式选择收款账户，金额弹窗展示完整收款人及账户，再点击微信充值；现有 `RechargeViewModel`、微信唤起与查单流程直接复用，不创建第二套支付逻辑。
- 订单查询仍校验本次订单号、目标、金额、实付金额、支付方式和收费项目；预支付响应如果回显了冲突的 `third_party` 则拒绝唤起。不会用付款人余额变化判断收款人到账。
- 验证码图像、查询密码、身份证 / 学工号、收款目标和订单只在内存中使用，不存到 SavedState、文件或日志；密码提交后清空界面输入，写操作不自动重试。
- 已有接口构造、错误分支、状态管理、支付复用和浅色 / 深色 UI 的离线测试。实际代充值扣款 / 到账未专门测试；这是验证说明，**不作为实现前置条件，也不要求用户为了验证支付一笔**。


## 8. 查询与确认两步交互

- 查询页只包含学工号 / 证件号选择、查询对象、图形验证码和“查询”按钮。验证码图片在左，输入框在右；点击图片刷新并清空验证码，不显示独立“刷新验证码”文字按钮。
- 查询成功进入收款账户确认页，隐藏查询方式、查询对象输入和验证码输入。显示后端返回的完整姓名、学工号、账户名称 / 账户 ID，方便区分候选；仅 `toString()` 和日志保持敏感信息保护，界面不额外打码。
- 用户明确选定收款账户后可继续。确认页提供“上一步”，返回时保留原查询方式和对象，只清除候选、已选目标、旧验证码 / 输入，并请求全新验证码；须用户重新输入后才能再次查询。
- 选定目标后复用充值金额界面、微信支付和查单。上述显示 / 返回 / 验证码清空有离线 UI 和视图模型回归覆盖，不要求实际付费测试。

## 9. 选中态与底部安全区

收款目标未选中为灰底 / 深色字，用户选中后使用主题强调色底和 `onPrimary` 文字（默认蓝底白字），显示“已选择”。底部确认 / 查询 / 充值按钮通过共享 `bottomSheetSafeArea` 留出导航栏安全区；导航栏与 IME 使用 union 取较大 Insets，并消费已经应用的 Insets，避免重复叠加。已覆盖实际 Compose 导航栏 Insets 注入、未选 / 已选像素颜色、重复 Insets 消费和 IME 较大值的离线测试。


## 10. 已验证的挂失目标支付拒绝（2026-10-22）

用户提供的代充值 HAR 中，收款卡 `lostflag=1`，查询成功、10 元订单创建及收银台读取均成功，但获取微信支付参数返回 `code=60007`、`success=false`、`data=null`、`msg=账户已挂失`。未拉起实际支付。原生共用充值层现在原样显示此原因并结束尝试，不进入待支付或结果未知，也不自动查单／重试。完整处理与验证边界见 `recharge.md` 的挂失充值拒绝一节。原生查询阶段若只有挂失／冻结目标，按官网状态文案提示，不再只说没有正常账户。
