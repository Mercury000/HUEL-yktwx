## 与非零用量接水对照

此前 `饮水.har` 在同一结束状态返回 `amount=1`，随后调用 `/order/afterPay/creating` 创建后付订单，再调用 `/order/sync` 处理订单。零用量抓包在设备结束后没有这两个调用。

`amount` 的单位尚无依据，不能直接作为金额或水量展示。仅使用其明确为零的情况选择结束处理分支，不展示“0 元”或声称支付已完成；缺失、null 或无法解析的值均不视为零。

## 当前接水处理

1. 先匹配本次 orderNo 与设备 identify。其他订单的结束响应不能结束当前接水。
2. 仅当 `status=5、workStatus=1` 时进入已有的“接水已结束”页面。
3. `amount` 明确为数值零时，保存已结束且处理完成的会话，跳过后付创建与同步。重新进入或重试不会补发这些请求，可以再次扫码。
4. 其他情况继续原有后付创建与同步流程；不读取账单、不推算费用。
5. 设备已经返回结束后，后付字段缺失或网络异常不能把会话恢复成接水中。保留已结束状态，在页面显示错误供重试。

原实现没有零用量分支，设备结束后仍调用后付创建，并要求返回 orderNo 和 orderId。这里的“设备响应信息不完整”是本 APP 的必填字段检查错误，不是设备返回的扣费失败结论。新抓包提供了跳过零用量后付流程的依据。

该规则仅适用于接水。`桶自洁.har` 的零元洗衣程序仍有创建、支付处理及设备启动请求，不能因零元套用接水规则；详见 `life-devices-laundry.md`。

## 验证范围

定向验证接水 API 和 ViewModel：明确的数字零与字符串零、非零、缺失、null 和不可解析的 amount；零用量结束后不创建或同步后付订单；重新进入、重试和再次扫码；后付字段不完整时保持已结束；原有非零接水流程。

仅使用离线响应和测试替身，未重放抓包或操作真实设备。洗衣的实现与验证见 `life-devices-laundry.md`；账单暂不接入。

## 首页返回入口补充

正在启动、接水中和正在结束的接水会话通过共用 miuix 状态卡显示在首页，洗衣同时进行时分别显示。大厅顶部也显示相同会话入口；点击回到当前进度，不重新扫码或重复启动。服务端确认接水结束后移除进行中的首页入口，结束详情仍能从接水入口打开。接水与洗衣分别持续读取已有订单，后台暂停，返回前台恢复；读取错误保留各自归属，不增加“待确认”业务状态。
