# 财小通：友盟 U-App 免费版统计上报设计

设计日期：2026-11-12。

本方案从产品要回答的问题出发设计，采用官方 Android 统计 SDK、标准设备用户与会话统计，以及免费版原生报表。工程已按本方案接入 SDK 与业务埋点，仅使用正式应用的一套 AppKey 和 `official` 分发渠道；正式应用的 19 个事件及中文显示名称已创建并回查一致，实机发送与后台报表验证尚待完成，详见 [接入说明](umeng-analytics-integration.md)。

## 1. 统计目标

只回答四组问题：

1. 应用近期有多少活跃设备用户、新增设备用户、启动，哪些版本仍在使用？
2. 付款码、账单、充值缴费和生活服务分别有多少设备用户使用、使用多少次？
3. 用户实际遇到了哪些功能故障，手动登录是否经常失败？
4. 新版有没有被发现，下载是否完成，是否交给系统安装？

默认范围为 19 个自定义业务事件、10 个事件参数绑定。日常看昨日及最近 7/30 日趋势，不依赖实时数据、付费 SQL、留存、个人细查或高级漏斗。

“用户”按友盟设备识别口径解释，不等于学校账号数或真实个人数。清除数据、重装、标识变化及多设备会影响设备去重结果。

## 2. 由 SDK 提供的基础统计

使用官方 SDK 的基础用户和启动统计，不自行生成长期安装标识，不修改 SDK 的用户或会话身份。

| 内容 | 使用方式 | 解释 |
| --- | --- | --- |
| 活跃设备用户 | 基础用户报表，按日及平台实际支持的周期查看 | 近期实际运行且被统计到的设备用户 |
| 新增设备用户 | 基础新增用户报表 | 首次被 SDK 识别的设备用户；不表示 APK 下载或系统安装总量 |
| 启动次数、会话 | 官方 SDK 负责生命周期识别 | 遵循 SDK 的启动和会话口径，不自行将每次页面切换视为启动 |
| 应用版本 | SDK 读取实际运行版本、构建信息 | 看版本活跃规模及趋势；版本累计用户不能直接相加当全应用去重人数 |
| 分发渠道 | SDK 的 channel | 记录实际安装构建的分发来源，不能用用户选择的更新通道覆盖它 |
| 系统和终端信息 | 使用 SDK 的标准环境采集 | 不另发环境快照，不默认展示 Android、中国这类缺乏区分度的图 |

不额外定义 app_open、installation_first_seen、environment_snapshot 等事件。基础 SDK 不会自动识别下面的业务行为，业务事件需要明确埋点。

页面统计选择官方手动模式；本方案不额外调用通用页面访问统计接口。账单明细和账单统计是需要单独衡量的功能，使用下述业务事件。默认不采集所有页面、页面路径或页面停留时长。

## 3. 事件目录

所有事件均为普通多参数事件，代码使用稳定英文 ID，后台设置中文显示名称。

关键功能各自使用一个事件名，直接获得该功能的每日事件次数和每日独立设备用户数。参数只承担补充分类，不把“参数次数分布”当成“该分类的独立用户数”。

### 3.1 付款码与账单：4 个事件

| 事件 ID | 中文显示名称 | 触发条件 | 参数 |
| --- | --- | --- | --- |
| payment_code_shown | 展示有效付款码 | 每次实际进入可交互付款页后，首次展示当前有效码时记录一次 | 无 |
| bill_list_viewed | 查看账单明细 | 用户实际进入并看到可交互的账单明细页 | 无 |
| bill_stats_viewed | 查看账单统计 | 用户实际进入并看到可交互的账单统计页 | 无 |
| bill_filter_applied | 使用账单筛选 | 用户确认搜索、筛选、日期范围或清除筛选后记录一次 | filter_kind |

付款码自动换码不重复记。一次付款页进入中先失败、随后恢复亮码，可以先记明确故障，再记一次亮码；亮码不表示完成消费。

账单页面首次可见以及离开后再次进入可以计数；预加载、重组、旋转、短暂系统弹窗遮挡后恢复不新增一次访问。搜索只在确认时记录，不按输入字符记录。

### 3.2 充值缴费：6 个事件

| 事件 ID | 中文显示名称 | 触发条件 | 参数 |
| --- | --- | --- | --- |
| recharge_self_submitted | 提交本人充值 | 输入校验通过，实际开始一次充值提交 | 无 |
| recharge_other_submitted | 提交代人充值 | 输入校验通过，实际开始一次代人充值提交 | 无 |
| fee_electricity_submitted | 提交电费缴费 | 输入校验通过，实际开始一次电费缴费提交 | 无 |
| fee_water_submitted | 提交水费缴费 | 输入校验通过，实际开始一次水费缴费提交 | 无 |
| fee_network_submitted | 提交校园网缴费 | 输入校验通过，实际开始一次校园网缴费提交 | 无 |
| fee_utility_submitted | 提交水电合缴 | 输入校验通过，实际开始一次水电合缴提交 | 无 |

打开弹窗、填写信息、输入校验失败、重复点击被拦截均不上报。一次提交里的网络重试不另算一次提交；失败后用户明确重新提交，可以算新的逻辑尝试。

本组指标名称固定为“提交次数”和“提交设备用户数”。不记录完整支付生命周期，不将跳转支付、余额变化或待确认状态解释为支付完成，不计算严格支付成功率。

### 3.3 生活服务：4 个事件

| 事件 ID | 中文显示名称 | 触发条件 | 参数 |
| --- | --- | --- | --- |
| panggui_water_start_requested | 提交胖乖接水 | 校验通过，实际开始一次接水启动请求 | 无 |
| panggui_shower_start_requested | 提交胖乖淋浴 | 校验通过，实际开始一次淋浴启动请求 | 无 |
| panggui_laundry_pay_submitted | 提交胖乖洗衣付款 | 校验通过，实际开始一次洗衣付款请求 | 无 |
| hui798_water_start_requested | 提交798开水 | 校验通过，实际开始一次798用水启动请求 | 无 |

这一组衡量功能提交，不宣称设备已成功启动、洗衣已启动或已经完成服务。不记录停止、关水、每轮状态轮询、设备恢复观察和实际用水/洗衣时长。

### 3.4 登录与故障：2 个事件

| 事件 ID | 中文显示名称 | 触发条件 | 参数 |
| --- | --- | --- | --- |
| login_result | 手动登录结果 | 用户主动发起的真实登录流程，得到一次明确成功或失败结果 | platform、outcome；失败时带 error_kind |
| operation_failed | 功能明确失败 | 付款码、充值缴费或生活服务发生一次明确、影响用户使用的最终失败 | feature、error_kind |

login_result 不记录静默登录恢复、正常自动续期、每次账户状态检查；用户输入校验失败或取消也不记录。登录人数是“发起手动登录并得到结果的设备用户”，不能作为已登录用户总数。

operation_failed 包括：没有有效付款码且取码最终失败；充值缴费提交被明确拒绝或请求最终失败；生活服务启动或付款请求明确失败。它不包括待确认、取消、轮询中间错误以及后台无用户影响的失败。

同一逻辑尝试或同一连续亮码故障阶段只记录一次最终故障。用户明确重新尝试失败，可以新增一次。登录失败和更新下载失败各自在专属结果事件里记录，不再同时发送 operation_failed。

本组默认看故障次数和分类分布。operation_failed 的独立用户数表示当天遇到任一种所列故障的设备用户；不承诺仅凭参数分布即可得到每种故障的独立用户数。

### 3.5 应用更新：3 个事件

| 事件 ID | 中文显示名称 | 触发条件 | 参数 |
| --- | --- | --- | --- |
| update_available | 发现新版 | 合法更新清单验证后，确认有适用于当前安装的较新版本 | target_version、update_channel |
| update_download_result | 更新下载结果 | 一次真实下载尝试得到成功或明确失败结果；成功必须包含 APK 完整性与身份校验通过 | outcome；失败时带 error_kind |
| update_install_handoff | 打开系统安装流程 | 应用成功发起系统安装界面或安装交接流程 | 无 |

同一次连续前台使用阶段，对同一目标版本只记一次 update_available。这个去重窗口由应用自己的前后台状态维护，不假设能读取 SDK 的私有会话 ID。

不记录每次自动检查、没有新版的检查、加入已有检查、下载进度、内部重试。用户取消不记下载失败。单纯重用已存在的 APK 不伪造一次下载结果。安装交接不表示安装完成；新版的后续使用由 SDK 版本报表观察，不建立逐设备升级链路。

## 4. 参数合同与额度

默认只使用下表中的分类字段，不为每个事件复制一整套环境或状态属性。全部参数使用字符串，首发后不改变同名参数类型。

| 参数 | 出现在哪个事件 | 允许值 |
| --- | --- | --- |
| filter_kind | bill_filter_applied | search / type / amount / date / combined / clear |
| platform | login_result | campus / panggui / hui798 |
| outcome | login_result、update_download_result | success / failure |
| error_kind | login_result、operation_failed、update_download_result | offline / network / timeout / auth / business / parse / integrity / permission / external / unknown；只在明确失败时传 |
| feature | operation_failed | payment_code / recharge_self / recharge_other / fee_electricity / fee_water / fee_network / fee_utility / panggui_water / panggui_shower / panggui_laundry / hui798_water |
| target_version | update_available | 已验证清单中的版本号，不包含地址或自由输入 |
| update_channel | update_available | stable / beta；表示本次发现更新所用通道 |

按事件与参数的绑定计数：账单 1 个、登录 3 个、故障 2 个、发现新版 2 个、下载结果 2 个，共 10 个。事件名 19 个，低于已公布免费版 100 个事件、50 个参数、1000 个参数值的额度。

target_version 的不同取值随发布增加，实施时需要观察参数值额度；其他字段均为固定小枚举。额度的后台统计粒度以实际控制台为准，不将此设计计数当作账号实际余额。

支付方式暂不采集。只有存在多种实际可选方式，且确实需要据此做产品决策时，才给相应提交事件增加 payment_method。设置快照、设置修改、头像、码号显隐、房间管理、校园卡管理和扫码细节默认不纳入本方案。

不增加 event_id、attempt_id、session_id、installation_id、event_time 等业务参数。操作去重状态只在本地维护，事件时间由 SDK 管理。

## 5. 原生报表与指标口径

| 看板 | 展示内容 | 解释 |
| --- | --- | --- |
| 应用使用 | 活跃、新增、启动趋势 | 使用 SDK 的基础报表口径；优先看昨日及完整日期 |
| 版本使用 | 各版本活跃用户与趋势 | 看实际运行情况，不称为当前安装存量 |
| 核心功能 | 亮码、账单明细、账单统计、筛选的次数和每日独立用户 | 页面可见与实际亮码分别定义，但不再记录所有普通页面 |
| 充值缴费 | 6 种提交的次数、每日独立用户 | 直接按事件查看，不把次数当人数 |
| 生活服务 | 4 种提交的次数、每日独立用户 | 明确是提交，不能解释为成功完成服务 |
| 故障与更新 | 故障次数及分类、登录结果、发现新版、下载结果、安装交接 | 结果分布不自动等于严格转化漏斗 |

### 单日功能使用率

当天某功能独立设备用户数 ÷ 当天全应用活跃设备用户数。

例如，某日全应用活跃 300 个设备用户，60 个至少一次提交电费，则当天电费提交使用率为 20%。这是全应用日活中的使用率，不是校园登录用户或具备缴费条件用户中的覆盖率。

只对参与基础统计的有效前台使用记录计算该比例；业务埋点不能在未统计到前台使用的情况下，凭后台回调制造功能活跃用户。授权变化后的旧任务回调不补记新的使用尝试。

### 单日使用频次

当天某功能事件次数 ÷ 当天该功能独立设备用户数。

例如，当天 20 个设备用户确认筛选 80 次，则当天每个筛选使用设备平均确认 4 次。

### 多日查看

事件接口已确认提供每日次数与每日独立用户趋势。近 7/30 日可以看总次数、日均独立用户、每日使用率和趋势。

不能把每日独立用户相加称为周/月去重用户。需要合并多个事件的使用人数时，也不能相加各事件人数。平台是否提供免费跨日去重、跨事件去重以及参数筛选后的独立用户，应按实际报表验证；本方案的默认指标不依赖这些能力。

按版本查看基础用户规模与按版本查看某事件是两个报表路径。普通事件 OpenAPI 没有版本/渠道过滤，不能给它添加不存在的参数。功能按版本的进一步比较，使用实际账号有权限的原生事件维度报表验证后再纳入。

不计算严格支付成功率、设备实际启动成功率、安装完成率、真实停留时长或留存。普通结果分布可以帮助排错，不建立逐订单和逐设备服务轨迹。

## 6. 授权、采集边界与数据隔离

- 同意当前应用使用与隐私说明后才初始化统计 SDK、记录和上传；不设置独立统计开关。
- 已有有效同意记录时，在 release 的 `Application.onCreate()` 初始化 SDK，早于首个 Activity 创建；首次接受须知时再延迟初始化。Application 初始化不提前开启业务事件，业务操作仍由实际前台状态控制。
- 对照最终 SDK 版本披露设备标识、设备环境、网络信息和友盟作为接收方，不将友盟设备统计描述成只有每日变化的匿名标识。
- 基础设备识别由 SDK 负责；不调用账号绑定、手机号、邮箱或用户属性接口，不上传校园账号、生活平台账号或自建长期 UUID。
- 仅使用正式友盟应用的一套 AppKey；release 接入 SDK，通过官方扫码模式验收，由 SDK 隔离集成测试数据。debug 与开发预览不包含 SDK，使用统一的停用实现，不另外接入测试应用。
- 正式 stable/beta 可以共用正式应用，以实际版本和安装渠道区分。channel 与 update_channel 含义不同。
- 只接入基础统计所需组件，额外推送、广告、卸载识别或高级运营组件不属于本方案。
- 统计任务不影响取码、登录、付款和设备操作。统计失败不转换为业务失败，不向用户弹统计故障提示，不为埋点额外请求学校或生活平台接口。
- 授权撤销后立即使本地操作凭据失效，停止新增业务统计，并调用官方 `MobclickAgent.disable()`。已进入 SDK 队列的数据仍可能发送，不承诺撤销会自动删除已入库历史。所选 SDK 没有公开的对称重新启用接口；同进程重新同意后保持统计停用，下次冷启动读取有效同意后恢复。

业务参数不含学工号、姓名、手机号、Token、密码、验证码、卡号、付款码内容、原始扫码内容、订单号、房间、设备序列号、账单、商户、余额、金额、搜索原文、图片，以及上述内容的哈希。错误只传固定分类，不传异常原文、完整日志、URL 或响应内容。

## 7. 历史查询与免费权益

官方结果指标调整通知明确：自定义事件的次数、独立用户数、时长及属性分布支持近 2 年结果查询。此方案据此承诺事件报表的历史回看范围，不承诺永久保存。

全应用日活、新增、累计用户等基础结果的独立历史期限，未在该通知中明确，不将事件的两年期限自动套用到所有基础报表。

免费套餐明确不提供实时数据；主看板以昨日及以前的完整数据为主。留存、高级分析的免费权限在不同官方页面表述不完全一致，默认指标不依赖这些功能。

需要超过两年的事件趋势时，可另行安排汇总报表导出；导出属于后续独立功能，不隐含在本次设计里，也不导出设备级行为记录。

## 8. 实施时的最小验证

实施只对 SDK 接入与埋点的直接路径做定向验证：

1. 同意前没有统计初始化或上传；仅正式构建使用正式 AppKey，调试和预览保持停用。
2. 各事件的有效触发、重复点击、重组、轮询和重试去重正确。
3. 失败分类不含自由输入或敏感业务内容；取消、待确认不当失败。
4. 用户首次同意、撤销和旧异步回调的授权边界。
5. 测试设备同日多次触发同一事件：次数增加，独立设备用户数按后台实际识别结果核对。
6. 免费后台的中文显示名称、19 个事件注册与参数配额，以及次日数据可见。

按所改 SDK 接入与埋点路径选择检查，不默认进行全量测试。
