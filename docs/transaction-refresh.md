# 交易后的余额、账单与统计刷新

充值／缴费订单成功与余额、账单搜索、统计接口的更新时间可能不同。旧实现只失效一次缓存并读取一轮；一轮成功但内容仍旧的响应会重新获得 60 秒缓存有效期。本次补充只读查询的有限补查与待刷新状态，不改变支付结果判据。

## 触发与范围

- 本人充值成功使余额、账单、月度收支及收入图表失效；代人充值保留未知收支方向。
- 付款码确认扣款使账单、月度收支及支出图表失效；已取得的余额不重复查询。
- 普通取码、手动余额查询、回前台查询取得同账号同账户的新余额时，也通知账单与月度收支失效。首次有效网络读取、本地缓存恢复、账号或付款账户切换不计算余额变化；余额变化通知不展示交易成功反馈。
- 缴费成功增加所属项目信息；宿舍补查只读取受影响项目及配对表必须的配置。

## 缓存与补查

- 正常读取继续复用 60 秒缓存。失效后的读取与本轮开始前的有效网络快照按查询键比较，列表、收支、笔数、趋势、分类、排行分别跟踪。
- 成功返回相同内容不会解除待刷新状态；内容变化只表示该数据观察到了更新，不证明某笔交易已经入账。
- 没有原网络基线时，第一份响应先建立比较基线，保守地保持待刷新。
- 查询可见页面的数据。充值结果弹窗关闭后再执行相关读取；离开页面、覆盖弹窗、切后台或离线时暂停补查，保留状态与已用预算。
- 一次初始查询后最多补查三次，分别在上一轮结束后等待 2、5、10 秒；后续补查静默进行，只查询尚未观察到更新或读取失败的部分。未查询部分保留原有错误，失败不会重新获得缓存有效期。
- 手动刷新取消同一数据的排队补查，并与在途请求合并；返回页面不重置补查预算。
- 预算用完只停止定时请求。待刷新数据下次进入仍需联网，缓存只用于先展示；不通过固定超时把旧响应重新标记为新鲜。
- 新事件撤销旧读取版本；被取消或迟到的响应不能确认新一轮更新。退出／切换账号清理比较基线与定时任务。

保守策略的代价是：合法但一直不变的查询结果（例如筛选不包含新交易或排行未变化）可能持续在进入时联网一次。自动补查仍有上限，不做无限轮询；日期不包含当前交易、收支方向不相关的图表不启动补查。

## 验证

`TransactionRefreshTest` 使用虚拟时间验证退避、预算、隐藏／返回、手动请求合并、账号清理和读取版本。

`TransactionDataRefreshTest` 使用虚构服务验证余额变化事件、独立延迟、超出补查预算、同一缓存窗口内返回、迟到响应、月度指标选择性刷新、项目与收支图表范围。

`TransactionNavigationTest` 通过实际应用页面与按钮验证完成／返回关闭、余额先更新而账单随后更新，以及回到“我的”刷新月度收支。全部回归不连接真实支付接口，也不要求实际消费或充值。
