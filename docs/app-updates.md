# 应用更新

客户端已改为读取 GitHub/CDN 的签名静态清单，在本机比较 `versionCode` 和 Android API 级别，使用应用内下载器及系统安装器。更新检测不再调用自建 `cxt` 服务。现有服务器需要在迁移期继续服务尚未升级的旧客户端。

## 用户交互

| 入口/状态 | 行为 |
| --- | --- |
| 自动检查，普通更新 | 登录页和四个主 tab 共享横幅，不主动弹详情 |
| 手动检查，普通更新 | 直接显示详情；加入自动请求时也获得一次明确结果 |
| 点击横幅 | 显示同一详情 |
| 手动无更新/失败 | Toast；自动无更新/失败保持静默 |
| 忽略 | 关闭详情，保留已知版本及设置入口红点 |
| 跳过此版本 | 持久记录版本，隐藏该版本自动横幅；手动检查仍能查看 |
| 横幅关闭按钮 | 同版本暂停自动提醒 24 小时，不影响新版本和手动检查 |
| 强制更新 | 根界面阻断登录和业务页面，不能返回/外部点击关闭，无跳过和忽略 |
| 下载、校验、授权或安装失败 | 正文末尾复用 `InlineError`，主按钮提供对应重试操作 |

版本、按设备时区/语言格式化的发布时间、Markdown 日志及内联错误共用限高滚动区。三个操作固定在正文之外，窄屏使用两行次要按钮和整行主按钮。下载中不关闭详情、不重复启动任务；主按钮位置及最小高度不随进度变化。

沿用现有成功 24 小时、失败 1 小时的前台检查冷却。手动检查绕过冷却和跳过记录，自动、手动共用一个活动会话。“普通更新提醒”开关只控制普通更新的自动横幅：关闭后仍会静默检查，保留检查冷却、手动检查结果及新发现或已确认的强制更新提示，也不取消正在进行的检查和用户打开的详情。沿用旧偏好存储键，保留用户已有的开关选择。未同意须知时不联网、不展示缓存提醒。

更新检查总时限为 3 秒，两个渠道并发处理；单次元数据请求限时 1.5 秒，每个渠道等待首个可采用结果最多 2.5 秒。首个来源完成签名、渠道、版本和有效期校验后，另行保留完整的 300 毫秒收敛窗口，继续接收窗口内返回的所有来源，不因第二个有效结果到达而提前结束；全部来源已结束时可立即返回。GitHub 未返回不阻塞已验证的 CDN 结果；权威源确认首次清单不存在时也仅保留同样的短收敛窗口。已收到的结果仍按权威优先、签名有效和冲突拒绝规则选择；平台 DNS 或读取未及时响应取消时，检查调用不等待阻塞网络线程。APK 下载沿用独立的下载超时设置。

## 元数据与信任

- `updates/public-key.txt`：客户端编译时嵌入的 Ed25519 SPKI DER 公钥（Base64）。
- `updates/policy.json`：在 `main` 分支按 stable/beta 管理人工强制边界及原因。初始边界均为 0。
- `updates/sources.json`：发布时探测的 APK CDN 候选池。
- `updates/{stable|beta}/latest.json`：签名的可变指针。
- `updates/{stable|beta}/manifests/{revision}-{sha256}.json`：签名的不可变清单，文件名摘要绑定清单文件字节。

以上 `latest` 和 `manifests` 由发布工作流生成，当前代码接入不创建虚假的发布清单。

签名封套：

```json
{ "algorithm": "Ed25519", "payload": "Base64 的 UTF-8 JSON 字节", "signature": "Base64 签名" }
```

签名直接覆盖 payload 原始字节，避免跨语言 JSON 重排导致验签分歧。latest 的 payload 包含 `schemaVersion`、`channel`、`policyRevision`、`manifestPath`、`manifestSha256`、`expiresAt`。客户端分别验证指针签名、清单文件摘要和清单签名，再比对渠道、revision 及有效期。

清单 payload 必含 `schemaVersion=1`、`channel`、`packageName`、`versionCode`、`versionName`、`minSdk`、`changelog`、`maxForcedVersionCode`、`policyRevision`、`urls`、`sha256`、`size`、`releaseUrl`、`expiresAt`；`publishedAt` 用带时区的 ISO 时间传输。展示时缺失/非法发布时间隐藏，不显示原始字符串。数字字段拒绝字符串、浮点和布尔类型。

七个元数据入口并发读取：GitHub Contents API 是唯一权威源，Raw、jsDelivr、Fastly、Gcore、TestingCF、Statically 提供镜像。权威源可用时，额外收集 700ms 内的镜像以识别同 revision 冲突；权威不可用时选签名有效的最高 revision。请求有 HTTPS、超时、1MiB 响应上限、缓存控制及 cache-buster；取消时关闭连接。

持久保存最高 revision、内容摘要、版本和强制边界，跨安装版本保留。拒绝低 revision、同 revision 内容冲突、版本下降和强制边界下降。签名清单默认有效 90 天；过期后不能作为新的检查结果或启动下载，已确认的强制状态继续保留。当前进程中的普通提示也会在返回前台或检查完成/失败时清除过期目标；下载/校验期间跨过有效期时，启动安装器前再次拒绝过期清单。可通过手动重发已有 Release 刷新有效期。

应用设置提供“接收测试版更新”。初始渠道取安装包内嵌渠道，并立即保存；之后用户选择跨版本、跨 stable/beta 安装保留。stable 订阅只检查 stable；beta 订阅同时检查 beta 和 stable，选择合法的较高 versionCode。切换会取消旧检查/下载，清除旧渠道普通提示，并在前台有联网授权时立即重查；切回 stable 不降级，等待更高编号的正式版。

任一渠道缺失或所有来源暂时不可用时，beta 检查仍可采用另一个渠道的可信结果；签名错误、冲突或策略回退不能作为普通断网忽略。已确认的两个渠道强制边界均持久保留，切换订阅不会解除；必要时继续展示原 beta 强制目标。Android UI preview 构建仍不会请求元数据，也不等同于 beta 发布。

## 强制边界

`currentVersionCode <= maxForcedVersionCode && latestVersionCode > currentVersionCode` 时需要更新。发布时校验 `0 <= maxForcedVersionCode < latestVersionCode`。后续 Release 不自动归零，也不能低于已发布边界。Actions 自动递增 revision，每次实际内容或策略变化使用新 revision；失败遗留的不可变清单也会占用 revision。

只有读取实际安装版本确认已超过强制边界才解除。下载失败、拒绝授权、取消安装、断网和关闭普通更新提醒均不能解除。强制目标没有兼容安装包时仍阻断并显示错误，需要发布方提供兼容制品。首次完全离线的客户端无法知道从未获取的新策略。

## APK 下载与安装

清单至少含五个不同主机的 HTTPS CDN 地址，加上末尾 GitHub 官方兜底。检查清单的来源与 APK 下载来源分别配置，不能用清单响应速度代表 APK 下载速度。开始下载时，并发读取各 APK 来源的最多 16KiB 前缀，选源限时 3 秒；检查 HTTPS、HTTP 状态、声明大小和 ZIP 文件头，优先使用最先返回有效文件数据的来源，并取消剩余探测。选源失败明确提示网络错误，不继续长时间串行等待。

下载至应用私有目录的 `.download` 临时文件，检查大小、同步落盘并校验 SHA-256/包名/versionCode/当前签名证书，成功后原子重命名。重定向必须仍为 HTTPS。网络、大小或哈希失败删除临时文件并尝试下一源，按钮明确显示“重试下载”；通过哈希的文件若包名、版本、签名或系统兼容性不符，立即停止，不从其他来源重复下载相同字节。签名清单提供 `signerSha256` 时，下载前先与已安装应用的证书比较；旧清单无此字段仍保留安装前的实际 APK 签名检查。

选源、下载、校验期间禁用关闭，并由弹窗内部消费返回手势，避免播放关闭动画后又被恢复。下载百分比使用清单中的文件大小，传输阶段最高 99%，校验后才进入可安装状态。内联错误随出现和消失动画展开或收起，没有错误时不预留高度和额外间距。

已知长度显示确定进度，未知长度显示不确定进度；更新约 300ms 节流，校验前最高 99%。同一版本和 SHA-256 只有一个下载计划，变化时取消旧计划并隔离回调。关闭普通更新提醒保留正在下载的详情；失去联网授权而取消下载后恢复为可重试状态。进程结束后未完成的下载不续传；重新点击时清理临时文件，完整校验并复用匹配的已下载 APK。

每次安装以及未知来源授权返回后，都重新计算本地 SHA-256，并与当前详情的清单比对，再核对包名、versionCode 和签名。错误文件删除并重新下载。签名目前采用严格当前签名集合一致，不启用证书轮换。使用范围限于更新目录的非导出 FileProvider，不申请共享存储或通知权限。下载在前台启动，后台完成不会自动打开系统安装器；授权结果早于 RESUMED 时等待前台。安装仍由 Android 系统确认。

## Actions 发布顺序

1. main/beta 普通提交只构建；Release Please 自动提出对应分支的版本和日志 PR。合并版本 PR 后创建带 tag 的 Draft Release，构建并签名，上传 APK 后按分支公开正式版或 Pre-release。beta 不再按每次普通推送直接发版。
2. 显式调用 `publish-updates.yml`，解决默认 GITHUB_TOKEN 不触发 release.published 的问题。已存在 APK 时重试复用原制品。
3. 人工发布、main 中的策略/候选池变更和每日定时维护均可触发；也支持手动指定已发布 tag 补发。
4. 下载唯一 APK，用 aapt2/apksigner 从 APK 本体读取身份、检查非 debuggable、版本标签、渠道和预期签名证书。兼容 Build Tools 新旧的 `sdkVersion`/`minSdkVersion` 及 `Signer #1`/`V3.0 Signer:` 报告；多个方案的相同证书可以去重，任一其他证书仍拒绝。首次自动发布传入 keystore 公有证书指纹，后续清单保存 signerSha256；拒绝证书改变。
5. 计算官方 APK SHA-256/size，并发完整下载候选 CDN，核对内容；至少五个不同起始与最终主机通过才继续。直接重定向到 GitHub 的别名不计入 CDN 数量。
6. 合并 main 中的人工策略，生成并签署不可变清单。签名 payload 限制为 512KiB，完整响应不超过 1MiB，与客户端验签/传输限制一致。上传不可变清单后通过 Raw 实际校验文件摘要，再独立提交并原子切换签名 latest 指针。
7. 任何前置校验失败保留上一 latest。两个提交之间失败可遗留不可变清单，重试使用更高 revision。相同 Release/策略/日志/候选池且剩余有效期大于 14 天时去重。较旧 APK 不覆盖新指针。推送前同步远端，保留并发代码提交；策略或 latest 已改变时拒绝覆盖。
8. 每日北京时间 08:30 检查续期/遗漏发布，也修复已提交 stable 指针但未成功设置 GitHub Latest 的情况。临时下载与 CDN 错误最多尝试三次；签名及策略校验错误直接失败。stable 清单完成后才设置 GitHub Latest，beta 不抢占。

工作流共用 `app-update-metadata` 串行锁，使用最小 `contents: write` 和 GitHub secrets。分支规则若禁止工作流直接提交 main，需要为该发布工作流配置受控写入途径；不要强制覆盖分支。没有通过足够 CDN 的校验时，Release 可已存在，更新清单仍保持旧版，需要检查候选池并手动重试。

## 上线配置与验证边界

参见 `updates/README.md` 配置 `UPDATE_SIGNING_KEY`，参见 [自动构建与发版](releases.md) 启用 Release Please、统一编号和 beta 分支流程。完整版本名称读取 version.txt；正式/测试构建共用偏移加工作流运行编号。两份渠道 manifest 自动维护发布基线，合并 beta 后由正式版本 PR 确定正式名称。本次保留本地版本 1.4.1/9，没有推送、发布 Release 或安装。

更新请求与下载请求不携带学校/生活平台凭据。须知已同步改为 GitHub/CDN 静态清单和系统授权说明，正文哈希变化会复用既有须知重新同意流程。

自动/手动会话、签名/防回滚、冲突/过期、版本/兼容性、界面、下载 SHA 回退、安装身份和权限恢复使用定向测试验证。第三方 CDN 的实际可用性、线上仓库写权限以及真实设备的系统安装仍需首次发布/设备验收确认。

2026-11-12 的完整复核、定向测试范围、CDN 实测和剩余上线验收见 [更新系统全面复核](update-review.md)。
